# เอกสาร TGK BotTradeFramework

เอกสารทั้งหมดในโฟลเดอร์นี้เขียนเป็นภาษาไทย โดยชื่อคลาส ฟังก์ชัน ตัวแปร และเส้นทางไฟล์จะคงตามชื่อจริงใน Source Code เพื่อให้ค้นหาได้ง่าย

## เริ่มอ่านจากตรงไหน

1. [ภาพรวมสถาปัตยกรรม](Architecture/overview.md) — ภาพรวม Grid components ที่มีอยู่และความสัมพันธ์ระหว่างกัน
2. [Grid Identity](Modules/grid-identity.md) — การแยก Grid แต่ละ Instance ด้วย Instance ID และ Magic Number
3. [Grid Persistence](Modules/grid-persistence.md) — การบันทึกและกู้คืนข้อมูล Grid
4. [ระบบทดสอบ MQL5](Testing/mql5-test-framework.md) — วิธีทำงานของ TestAssert และ TestRunner
5. [คู่มือทดสอบ Grid](Testing/grid-testing.md) — รายชื่อ Test EA วิธีรัน และสถานะผลทดสอบ
6. [บันทึกการตัดสินใจ](Decisions/README.md) — เหตุผลสำคัญเบื้องหลังการออกแบบ
7. [บันทึก Phase](Phases/phase-grid-integration-testing.md) — สิ่งที่ทำและผลทดสอบใน Phase Integration Testing

## แบ่งหน้าที่เอกสาร

| เอกสาร | ใช้ตอบคำถาม |
|---|---|
| `PROJECT_STATUS.md` | ตอนนี้อยู่ Phase ไหน เสร็จอะไรแล้ว และขั้นตอนถัดไปคืออะไร |
| `README.md` ที่ Root | โปรเจกต์นี้คืออะไร และภาพรวมการใช้งาน |
| `Docs/Architecture/` | ส่วนต่าง ๆ เชื่อมต่อกันอย่างไร |
| `Docs/Modules/` | Module หนึ่งทำอะไร ใช้ข้อมูลอะไร และมีข้อจำกัดอะไร |
| `Docs/Testing/` | ต้องทดสอบอย่างไร และผลที่คาดหวังคืออะไร |
| `Docs/Decisions/` | ทำไมจึงเลือกวิธีออกแบบแบบนี้ |
| `Docs/Phases/` | Phase นั้นเปลี่ยนอะไร ตรวจสอบอะไร และผลเป็นอย่างไร |

## กติกาการดูแลเอกสาร

- เอกสารต้องอธิบายพฤติกรรมที่มีอยู่จริง ไม่ใช่สิ่งที่เราวางแผนจะเขียนในอนาคต
- แยกสถานะให้ชัดว่า **มีในโค้ดแล้ว**, **มีผลทดสอบยืนยันแล้ว**, **เป็นข้อกำหนดที่ตกลงไว้แต่ยังไม่พัฒนา**, หรือ **ยังรอตัดสินใจ**
- เมื่อเปลี่ยนโค้ด ต้องตรวจเอกสาร Module และ Architecture ที่เกี่ยวข้องด้วย
- เมื่อจบ Phase ให้อัปเดตทั้ง `PROJECT_STATUS.md` และเอกสารเชิงเทคนิค/บันทึก Phase ที่ได้รับผลกระทบ
- บันทึกผล Compile/Runtime ตามที่ผู้ใช้รายงานเท่านั้น ห้ามเขียนว่า Test ผ่านจากการตรวจโค้ดอย่างเดียว
- บันทึกเหตุผลการตัดสินใจที่ส่งผลระยะยาวใน ADR เพื่อไม่ให้ต้องเดาเหตุผลใหม่ในอนาคต
- ไม่สร้างเอกสารใหม่ซ้ำซ้อน หากสามารถอัปเดตเอกสารที่มีอยู่ได้
