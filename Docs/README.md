# เอกสาร TGK BotTradeFramework

เอกสารทั้งหมดในโฟลเดอร์นี้เขียนเป็นภาษาไทย โดยคงชื่อจริงของคลาส ฟังก์ชัน ตัวแปร Enum และเส้นทางไฟล์ไว้ตาม Source Code

## เริ่มจากตรงไหน

- [ภาพรวม Framework](Framework/README.md) — ขอบเขตของระบบกลางและหลักการแยก Shared Module ออกจาก EA
- [รายการ EA](EAs/README.md) — รายชื่อ EA ที่มีเอกสารใน Repository
- [Grid EA](EAs/Grid/README.md) — ภาพรวมและเอกสารของ Grid ที่กำลังพัฒนา
- [แนวทางการพัฒนา](Development/workflow.md) — Workflow การทำงานเป็น Phase และการดูแลเอกสาร
- [บันทึกการตัดสินใจ (ADR)](Decisions/README.md) — การตัดสินใจที่มีผลต่อ Framework หรือ EA เฉพาะตัว

หากต้องการทราบว่างานอยู่ในขั้นตอนไหน ให้ดู [PROJECT_STATUS.md](../PROJECT_STATUS.md) ซึ่งเป็นหน้าสรุปสถานะปัจจุบัน ไม่ใช่เอกสารอธิบายรายละเอียดเชิงเทคนิค

## โครงสร้างเอกสาร

| พื้นที่ | ขอบเขต |
|---|---|
| `Framework/` | สถาปัตยกรรมและ Module ที่ตั้งใจให้ใช้ร่วมกันระหว่าง EA หลายตัว |
| `EAs/<ชื่อ EA>/` | Logic, Architecture, Inputs, State Machine, Tests และข้อจำกัดของ EA นั้น |
| `Development/` | Workflow และมาตรฐานการพัฒนาที่ใช้กับทั้ง Repository |
| `Decisions/` | ดัชนี ADR และลิงก์ไปยังการตัดสินใจตามขอบเขต |
| `PROJECT_STATUS.md` | Phase ปัจจุบัน งานที่เสร็จแล้ว ผลตรวจสอบ และขั้นตอนถัดไป |

## กติกาการดูแลเอกสาร

- เอกสารอธิบายพฤติกรรมที่มีอยู่จริง ต้องไม่เขียนแผนงานให้ดูเหมือนพัฒนาเสร็จแล้ว
- แยกสถานะให้ชัดว่า **มีในโค้ดแล้ว**, **ผู้ใช้ยืนยันผลทดสอบแล้ว**, **เป็นข้อกำหนดที่ตกลงไว้แต่ยังไม่พัฒนา**, หรือ **ยังเป็นคำถามที่เปิดอยู่**
- วางเอกสารในระดับที่ถูกต้อง: Framework, EA เฉพาะตัว หรือ Development
- อย่าย้าย Module ไปอยู่ใน `Framework/` เพียงเพราะคิดว่า EA อื่นอาจใช้ได้ ต้องตรวจสอบขอบเขตและความรับผิดชอบก่อน
- เมื่อเปลี่ยนโค้ด ให้ตรวจเอกสารที่ได้รับผลกระทบ; เมื่อจบ Phase ให้อัปเดต `PROJECT_STATUS.md` และเอกสารที่เกี่ยวข้อง
- บันทึกผล Compile/Runtime ใน MetaEditor/MT5 ตามที่ผู้ใช้รายงานเท่านั้น
- บันทึกการตัดสินใจที่มีผลระยะยาวใน ADR พร้อมระบุ Scope ว่ามีผลกับ Framework หรือ EA ใด
- หลีกเลี่ยงเอกสารซ้ำซ้อน และตรวจสอบ Local Links หลังย้ายหรือเปลี่ยนชื่อไฟล์
